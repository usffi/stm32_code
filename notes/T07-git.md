## 一、自测（遮住答案先答一遍）

1. `.pio/` 为什么不能提交？三个理由，每个说一句后果。
2. `.gitignore` 的作用范围是什么？根目录的规则能管到 `t05/` 下面的文件，子目录的能管到根目录吗？
3. 冲突标记 `<<<<<<<` / `=======` / `>>>>>>>` 各代表什么？`git add` 在冲突解决里到底做了什么？
4. `fast-forward` 和 `--no-ff` 的区别？**团队为什么常要求 `--no-ff`**？
5. 已推送的 commit message 想改，会发生什么？为什么 hash 会变？
6. `git add -A` / `git add -u` / `git add .` 三者的范围差别？
7. `.gitignore` 的白名单写法（`*` + `!`）比黑名单好在哪？
8. 判断"一个提交只做一件事"的依据是什么？

<details>
<summary>答案（点开对照）</summary>

1. **体积**：一个工程 `.pio/` 几十 MB，六个工程几百 MB，GitHub 建议单仓库 < 1GB；**环境相关**：里面有绝对路径（`C:\Users\a3331\...`）、工具链版本、缓存，换电脑全失效；**会过时**：它是构建快照，改了代码它不变，提交进去反而误导。
2. `.gitignore` **只作用它所在的目录和子目录**。根目录的能管全局；`t01/t01-blink/.gitignore` 管不到 `t05/` 下的文件。规则叠加，不互相覆盖。
3. `<<<<<<<` 到 `=======` 之间是**当前分支（HEAD）**的内容；`=======` 到 `>>>>>>>` 之间是**要合进来的分支**的内容。冲突时索引里同一文件有 3 个版本（stage 1 祖先 / 2 我方 / 3 对方），`git add` 把它们**压成一个 stage 0**，Git 才知道"这个文件解决了"。不 add 直接 commit 会报 `Committing is not possible because you have unmerged files`。
4. **ff**：main 没动过，只是指针前移，不产生新提交，历史是一条直线，分支名消失。**--no-ff**：强制生成合并提交（两个父），留下分支边界。团队要求它是因为——**回滚能整块撤**（`git revert -m 1 <merge>` 一条命令撤掉整个功能，ff 只能逐个 revert）、**历史能看出功能边界**、**分支名留痕**。
5. message 是 hash 计算的一部分，改了等于**造一个新提交**，hash 完全变。要推就得 `--force` 覆盖远端；别人已拉过旧版本，本地与远端历史分叉，下次 pull 会出现重复提交或莫名冲突。所以共享分支一般禁止强推。
6. `-A` = 整个仓库的全部变化（含新文件）；`-u` = **只处理已跟踪文件**的修改和删除，新文件不碰；`.` = 当前目录及子目录的全部变化（在根目录时约等于 `-A`）。
7. 黑名单是"排除我想到的"，新出现的文件会被误提交；白名单是"只留我确认过的"，默认全挡。`**/.vscode/*` + `!**/.vscode/extensions.json` 就是白名单。
8. **这次提交能不能用一句话说完，而不需要加"顺便"**；再进一步：撤销它会不会连累别的东西。

</details>

## 二、一句话结论

> **Git 记录的不是文件，是"每次改动的快照 + 一句话说明"。** 分支只是指向快照的指针，合并是把两条指针线接起来；冲突是两条线改了同一处，Git 不替你决定。所以规范的本质是——**让三个月后的自己（和同事）能读懂、能回退**。

## 三、骨架（表格版）

### 3.1 日常四步

```bash
git status                    # 看有什么变了
git add -u                    # 已跟踪文件的修改/删除
git add <新文件路径>           # 新文件必须显式加
git commit -m "type(scope): 描述"
git push
```

### 3.2 三种 add 的范围

| 命令 | 加什么 | 会碰到新文件吗 |
| --- | --- | --- |
| `git add -u` | 已跟踪文件的修改 + 删除 | ❌ |
| `git add .` | 当前目录及子目录的全部变化 | ✅ |
| `git add -A` | 整个仓库的全部变化 | ✅ |

### 3.3 两种合并形态

| | fast-forward | `--no-ff` |
| --- | --- | --- |
| 触发条件 | main 在分叉后没动过 | 无论有没有分叉都强制生成合并提交 |
| 产生新提交 | ❌ 只挪指针 | ✅ 有 2 个父的 merge commit |
| `log --graph` 形态 | 一条直线 | `|\` + `|/` 的分叉 |
| 分支名留痕 | 消失 | 写在提交信息里 |
| 回滚 | 逐个 revert | 一条 `revert -m 1` 撤整块 |

### 3.4 冲突处理四步

```
① 打开冲突文件，找到 <<<<<<< / ======= / >>>>>>>
② 删掉这三行标记，保留你要的内容（可改写、可合并）
③ git add <文件>        ← 标记为已解决（索引压成 stage 0）
④ git commit            ← 生成合并提交（2 个父）
```

逃生：`git merge --abort` —— 回到合并前，一个字节都不变。

### 3.5 commit 规范

```
type(scope): 一句话说清改了什么

[可选正文：为什么改]
```

| 类型 | 什么时候用 |
| --- | --- |
| `feat` | 新功能、新代码 |
| `fix` | 修 bug |
| `docs` | 只动文档、注释 |
| `refactor` | 改结构不改行为 |
| `chore` | 目录调整、配置、杂务 |
| `test` | 只加/改测试 |

**scope 用包号**：`feat(t04)`，不是 `feat(04)`。

## 四、我原来错在哪

> ⚠️ **修正 1**：原文「`git add -A` 将已追踪文件全部提交」——**`-A` 是全部，含新文件**。只加已跟踪文件的是 `-u`。
> 这个区别很重要：`-u` 天然挡住"新生成的文件被误提交"（比如 `.vscode/tasks.json`）。

> ⚠️ **修正 2**：原文「内存占有太大」——是**体积**（占磁盘），不是内存（RAM）。嵌入式里这两个词不能混。

> ⚠️ **修正 3**：原文「在 2、4 行之间选一个留下或现在更改」——是"**自行**更改"。
> 而且关键点不是"选一个"，而是**可以自己改写合成一句**——你那次的 `# STM32 学习工程 dev合并冲突测试 test1` 就是这么来的，比选边更好。

> ⚠️ **修正 4**：原文「`--no-ff` 会把 main 和 dev 合并成一个新的节点」——准确说是「**生成一个合并提交，它有两个父提交**」。"两个父"才是它和 fast-forward 的本质差别。

> ⚠️ **修正 5**：原文「`feat(04)`」——scope 要写 `t04`，跟 `t05`/`t06` 保持一致。
